# CLI 出力の strict `cp932`（および GBK 以外のコードページ）対応・設計メモ

- 作成日: 2026-11-22
- 作成: Claude Code
- 担当: Claude Code
- ステータス: draft（直すかどうかをネモさんに決めてもらう。推奨は「案 A で直す」）

## 1. 目的

日本語 Windows で、CLI の出力をパイプ・リダイレクト・サブプロセスで受けたときに（stdout が strict `cp932` になったときに）、簡体字のメッセージで `UnicodeEncodeError` が出て CLI が止まる問題を、直すかどうか、どう直すかを決める。
`docs/plans/2026-11-19-upstream-check.md` の 2.(4) で「別の設計タスクとして扱う」とした残課題。

## 2. 調査結果

### 2.1 どこで、どう失敗するか（2026-11-22 に確認）

既存の `tests/test_cli_gbk.py`（合成データとモンキーパッチだけで、クラウドにもキーリングにも触れない）の出力先を、一時的に strict `cp932` に変えて流した（一時ファイルは削除済み）。**7 件すべてが `UnicodeEncodeError` で失敗した。**

| コマンド | 失敗する場所 | 原因の文字 |
| --- | --- | --- |
| `setup` | `src/mi_fitness_mcp/main.py:82`（最初の見出し `配置向导`） | `导`（U+5BFC） |
| `doctor` | `main.py:98`（最初の見出し `诊断`） | `诊`（U+8BCA） |
| `sync` | `main.py:165`（最初の見出し `同步`） | `步`（U+6B65） |

- **どのコマンドも、最初の 1 行目で落ちる。** 特に `sync` は、同期の処理を始める前に落ちるので、**データが 1 件も同期されない**。終了コードは 0 以外になる。
- 文字列の数で見ると、`main.py` の ASCII 以外の文字列 57 個のうち 39 個、`auth/__init__.py` の 5 個のうち 4 個が `cp932` に変換できない。どれも GBK には変換できる（上流の #22 が GBK だけを対象にしていた理由）。
- `argparse` のヘルプ文（`main.py:274` 以降の `help=`）も簡体字なので、`--help` をリダイレクトしても同じように落ちる。
- `export` のメッセージは英語だけなので、出力先のパスに `cp932` にない文字がない限り落ちない。
- `serve`（MCP stdio）は影響を受けない。`mcp.server.stdio.stdio_server` は `sys.stdout.buffer` を UTF-8 の `TextIOWrapper` で包み直して使っていて、`sys.stdout` のテキスト層を通らない。

### 2.2 起きる条件

- 対話コンソール（cmd / PowerShell / Windows Terminal）に直接出すときは、Python 3.6 以降は Windows の Unicode コンソール API を使うので起きない。
- パイプ（`|`）、リダイレクト（`>`）、別のプログラムからのサブプロセス実行（タスクスケジューラーのスクリプトで出力をログに書くときなど）では、`PYTHONUTF8=1` やシステムの UTF-8 設定がない限り、ANSI コードページ（日本語 Windows なら `cp932`）になって起きる。
- 同じことは `cp932` 以外でも起きる。英語版 Windows の `cp1252`、韓国語版の `cp949` などでは、簡体字はほぼすべて変換できない。つまり**日本語環境だけの問題ではない**ので、上流にも出しやすい。

### 2.3 いまの運用

- `PYTHONUTF8=1` で運用している（PROGRESS.md）。これを付けていれば起きない。
- 毎朝の CSV 出力（`MiFitnessDailyExport`）のスクリプトが `sync` をリダイレクト付きで動かしているか、`PYTHONUTF8=1` を付けているかは、まだ確認していない（Windows 側のスクリプトは読んでいない）。付けていなければ、`sync` が黙って 0 件のまま終わっている可能性がある。→ ネモさんに確認する。

## 3. 設計方針

### 3.1 推奨：案 A「出力できない文字だけを置き換えて、止まらないようにする」

`main()` の最初（`argparse` がヘルプを出す前）で、`sys.stdout` と `sys.stderr` について次のことをする小さな関数を呼ぶ。

- そのストリームのエンコーディングが UTF-8 系ではなく、`errors` が `"strict"` のときだけ、`reconfigure(errors="backslashreplace")` する。エンコーディングは変えない。
- `reconfigure` を持たないストリーム（テストで差し替えたものなど）は何もしない。

結果：
- UTF-8 の環境（`PYTHONUTF8=1`、Linux、macOS）と GBK の環境では、出力は 1 バイトも変わらない（簡体字はすべて変換できるので、置き換えが起きない）。
- `cp932` などでは、変換できない文字だけが `导` のような表記になり、**CLI は最後まで動く**。`sync` は普通に同期し、終了コードも正しく返る。`[OK]` / `[X]` などのマーカーと、日本語と共通の漢字はそのまま読める。
- 変更は `main.py` に 15 行ほど。上流のメッセージ（中国語）には手を入れないので、上流との差が小さく、そのまま上流にも出せる。

### 3.2 選ばなかった案

- **案 B：stdout を常に UTF-8 にする**（`reconfigure(encoding="utf-8")`）。リダイレクト先のファイルは読みやすくなるが、Windows で出力を `cp932` 前提で読むプログラムには文字化けになる。中国語版 Windows で GBK のつもりで受けている上流のユーザーの出力も変わってしまう。
- **案 C：CLI のメッセージを英語にする、または多言語化する**。上流は中国語を主にしていて、差分が大きくなりすぎる。上流のメッセージを直すたびに衝突する。
- **案 D：直さず、`PYTHONUTF8=1` の運用とドキュメントだけで済ませる**。コードは変わらないが、付け忘れると `sync` が 1 件も同期せずに止まる。毎朝の自動実行で気づきにくいのが困る。案 A と並べて、README に `PYTHONUTF8=1` を勧める一文を足すのはよい。
- **`errors="replace"`（`?` に置き換える）**：見た目はすっきりするが、何の文字だったかがわからなくなる。調べるときに困るので `backslashreplace` にする。

### 3.3 フォーク側への影響

- `docs/agent-collab`（毎朝の CSV 出力で使っている）にこの変更を入れると、`sync` などの CLI の出力が変わるのは「もともと落ちていた環境」だけ。いま `PYTHONUTF8=1` で動いているなら、出力は変わらない。
- 作業は `docs/agent-collab` から作業ブランチを切って行い、テストを通してから、PR（フォーク内）でマージする。上流にも出すなら、上流 PR のメモ（`2026-11-22-upstream-pr.md`）の 1 本として、上流 `main` から別ブランチを作る。
